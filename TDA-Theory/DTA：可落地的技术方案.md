#  TDA架构：可落地技术方案
## 一、总体架构概述

TDA架构的核心设计理念是：**LLM降级为“策略建议器”，所有输出必须以“事实+判例”双重校验方可放行**。空模型本身不生成任何内容，只做三件事——**空校验、空拦截、空增强**——像一个安检门一样，“空”着但通过规则过滤一切。

架构分为三层：
| 层级    | 名称	 | 功能	     | 状态    |
| ------- | --------- | --------------- |---------|
|第一层	 |  空模型校验层（NMP） | 目的→事实类型映射； 本地轻量校验	    | ✅ 已实现     |
|第二层		 | 结构化辩论层       | LLM生成 vs 空模型事实 → 冲突图构建	   |     理论完备  |
|第三层	 | 元受动极层	        | 裁决AI + 非认知熔断器 + 人工审计	   |  理论完备  |

## 二、第一层：空模型校验层（NMP）——已可部署
 这是TDA架构中唯一已有参考实现的部分。其核心组件包括：

### 2.1 核心组件
```
┌─────────────────────────────────────────────────────────────┐
│                    空模型校验层（NMP）                         │
├─────────────────────────────────────────────────────────────┤
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐   │
│  │   校验层      │    │  事实库       │    │  判例库       │   │
│  │ (拆解/提取/   │    │ (行业规则/     │    │ (历史错误     │   │
│  │  匹配/校验)   │    │  法规/参数)    │    │  归档)       │   │
│  └──────────────┘    └──────────────┘    └──────────────┘   │
└─────────────────────────────────────────────────────────────┘
```
-**校验层**：拆解用户指令、提取事实主张、匹配判例、校验LLM策略，拥有最终否决权

-**事实库**：存储行业规则、法律法规、设备参数、用户偏好等静态事实

-**判例库**：仅归档历史错误，同类场景自动拦截

### 2.2 运行流程

```
用户输入 → 目的解析 → 事实类型映射 → 事实库检索
    ↓
LLM生成策略建议
    ↓
后置冲突校验（LLM输出 vs 事实库+判例库）
    ↓
├─ 无冲突 → 放行
└─ 有冲突 → 拦截 + 记录判例

```

### 2.3 关键澄清

空模型不会做出任何判断；它只会计算是否匹配。就像防火墙不会“理解”黑客，它只会匹配规则。空模型是“可执行”的——它有通用的计算骨架（BFS、约束满足、路径选择），可以运行在任何领域，不需要重新训练。

### 2.4 性能指标

根据NMP参考实现的数据：

延迟：<5ms

存储：<100MB

可解释性：100%（每次拦截可追溯具体事实ID/判例ID）

### 2.5 部署方式

**NMP作为本地轻量校验层**，插在LLM的“策略输出”与“执行器”之间。它可以：

- 可插拔到任何LLM、任何终端

- 在云端-本地混合部署中，校验逻辑在本地执行，LLM在云端

- 事实库和判例库按行业/场景/用户个性化定制

## 三、第二层：结构化辩论层——设计规范

第二层实现“主动极”（LLM）与“受动极”（空模型+事实库）的**结构化对抗**。

### 3.1 核心机制：冲突图构建


```
                    ┌─────────────────┐
                    │   用户目的/问题   │
                    └────────┬────────┘
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
    ┌─────────────────┐           ┌─────────────────┐
    │  主动极：LLM     │           │  受动极：空模型    │
    │  (生成方案/策略)  │           │  (事实约束/校验)  │
    └────────┬────────┘           └────────┬────────┘
             │                             │
             └──────────┬──────────────────┘
                        ▼
              ┌─────────────────┐
              │  冲突图构建器     │
              │ (识别矛盾节点)    │
              └────────┬────────┘
                       ▼
              ┌─────────────────┐
              │  结构化辩论记录   │
              │ (可审计/可追溯)   │
              └─────────────────┘


```
### 3.2 关键设计原则

- **LLM不知道事实库的存在**：它只接收脱敏后的结构化事实，不知道哪些事实被过滤、哪些约束被启用

- **这不是两个AI“吵架”**：而是“形式推演”与“事实校验”之间的结构性质证

- **所有冲突节点被记录**：形成可审计的“辩论轨迹”

### 3.3 接口规范

```
# 第二层接口示意
class DebateLayer:
    def __init__(self, llm, null_model, fact_base, case_law):
        self.llm = llm              # 主动极
        self.null_model = null_model # 受动极
        self.fact_base = fact_base
        self.case_law = case_law
    
    def debate(self, user_purpose):
        # 1. 主动极生成方案
        proposal = self.llm.generate(user_purpose)
        # 2. 受动极提取事实约束
        constraints = self.null_model.extract_facts(proposal)
        # 3. 构建冲突图
        conflict_graph = self.build_conflict_graph(proposal, constraints)
        # 4. 返回结构化辩论记录
        return DebateRecord(proposal, constraints, conflict_graph)

```

## 四、第三层：元受动极层——设计规范

第三层实现**最终裁决**，包含裁决AI、非认知熔断器和人工审计。

### 4.1 三层裁决机制

```
                    ┌─────────────────────┐
                    │   第二层输出的冲突图   │
                    └──────────┬──────────┘
                               ▼
                    ┌─────────────────────┐
                    │   裁决AI             │
                    │  (动态阈值+有依据随机) │
                    └──────────┬──────────┘
                               │
              ┌────────────────┼────────────────┐
              ▼                ▼                ▼
    ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
    │  自动放行    │  │  自动拦截     │  │  转人工审计  │
    │ (低风险)     │  │ (高风险)     │  │ (不确定)     │
    └─────────────┘  └─────────────┘  └─────────────┘

```
### 4.2 裁决AI的严格限定

裁决AI不是又一个LLM，其权限被严格限定在**布尔操作空间**内：

- 只执行“匹配-比较-拦截”的形式化运算

- 不具备内容生成能力

- 动态阈值的调整范围由人类预设上下界

- “有依据随机”的每一次抽样都被完整记录、事后可审计

### 4.3 非认知熔断器

当系统触发以下条件时，无条件中断并等待人类接管：

- 裁决AI输出进入异常模式

- 连续多次触发拦截

- 系统检测到越狱尝试

### 4.4 人工审计

- 拥有最高否决权

- 所有裁决记录可追溯、可复盘

- 审计结果可沉淀为新判例

## 六、部署策略
### 6.1 混合部署架构

| 组件	    | 部署位置	 | 理由     |
| ------- | --------- | --------------- |
| LLM（主动极）	    | 云端	    | 计算密集，需要GPU集群       |
| 空模型（校验层）	    | 本地	       |   轻量（<5ms），保护事实库隐私  |
| 事实库		 | 本地        | 包含私域数据，不可上传  |
| 判例库  | 本地        | 包含敏感审计信息 |
| 裁决AI      | 本地+云端备份  | 核心裁决逻辑在本地      |
| 审计日志     | 本地  | 不可篡改，合规要求               |


### 6.2 “无资格原则”的实现

在云端-本地交互协议中，LLM：

- 不知道存在哪些事实

- 不知道哪些事实被过滤

- 不知道哪些约束被启用

- 不知道元事实库的存在

- 只接收脱敏后的结构化事实

**这是存在论隔离，而非权限管理**——即使LLM被攻击或越狱，也无法绕过元事实库的约束，因为约束在本地空模型中执行，不在云端。

## 九、方案的核心哲学依据
这个技术方案不是凭空设计的，它是论文中“受动-能动”辩证模型的直接工程化翻译：

|哲学概念|	工程实现|
| ------- | --------- |
|受动极（世界强制性反馈）|	空模型 + 事实库 + 判例库|
|能动极（主动组织解释）|	LLM（策略建议器）|
|实践中介（检验与重构）|	冲突校验 + 判例积累|
|受动极的最终校验权	|空模型的否决权 + 人工审计|
|非对称优先性	|LLM不知道事实库存在（存在论隔离）|
|“**判断归机，目的归人**”	|LLM负责生成，人类拥有最终否决权|

***空模型不是AI的“受动极”，而是人类受动极的制度化代理***。它不是AI“长出了”校验能力，而是人类为AI套上了“制度牢笼”。
